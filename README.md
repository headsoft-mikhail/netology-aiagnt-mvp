# MVP консультанта по сетевому оборудованию

Агент интернет-магазина подбирает домашнее сетевое оборудование и отвечает на
вопросы о выборе, совместимости и настройке. Инструкции и критерии выбора он
получает из локальной базы знаний через RAG, а цены, характеристики и наличие —
из SQLite-каталога.

## Возможности

- `search_knowledge_base` ищет подтверждённые сведения в базе знаний.
- `search_products` фильтрует каталог по категории, характеристикам, цене,
  бренду и наличию.
- CSV-слепок содержит 35 устройств пяти категорий; `product_code` — артикул
  товарной позиции.
- Long-term memory хранит только явно сохранённые предпочтения пользователя.
- Short-term memory поддерживает контекст текущей сессии.
- Trace показывает вызовы Tools, параметры, результаты, citations и
  использованные факты памяти.

Основной путь запроса:

```text
пользователь → AgentRunner → Memory → LLM-планировщик
             → обработчики → ToolRegistry
             → RAG и/или каталог → LLM → итоговый ответ
```

Основные компоненты:

- `src/ai_agent/agent.py` — оркестратор;
- `src/ai_agent/handlers/` — обработчики памяти, планирования, Tools и ответа;
- `src/ai_agent/tools/` — протокол, реестр и поисковые Tools;
- `src/ai_agent/rag/` — подготовка источников и retrieval;
- `src/ai_agent/catalog/` — CSV-слепок и SQLite-каталог;
- `src/ai_agent/memory/` — долговременная и сессионная память;
- `src/ai_agent/llm/` — Pydantic AI-клиент и типизированные ответы LLM;
- `src/ai_agent/service/` — FastAPI и app-scoped зависимости `modern-di`;
- `tests/` — unit-, сценарные и smoke-тесты.

## Установка

### Утилиты и зависимости

Локальная инструкция рассчитана на macOS. Нужны Homebrew и `just`; запуск на
других платформах не проверялся.

```bash
brew install just
just setup
just python 3.14.5
just install
```

- `just setup` устанавливает `pyenv` и `uv`;
- `just python` создаёт `.venv`;
- `just install` устанавливает основные и dev-зависимости из `uv.lock`.

Эти команды нужны для локального CLI, API и тестов. Для запуска только через
Docker нужны сам Docker и Just: `just docker_build` устанавливает
Python-зависимости внутрь образа.

### Переменные окружения

Создайте `.env` из шаблона:

```bash
just env_init
```

Команда не перезаписывает существующий файл. После создания `.env` обязательно
укажите вручную реальный `LLM_API_KEY` без кавычек; в `.env.example` токен
намеренно пуст. Настоящий `.env` не добавляется в Git.

### Конфигурация приложения

- Настройки читаются через `pydantic_settings`.
- Используются префиксы `LLM_`, `CATALOG_`, `MEMORY_`, `API_`, `AGENT_`, `RAG_RETRIEVAL_` и `RAG_PIPELINE_`.
- Вложенные поля разделяются `__`, например `RAG_PIPELINE_CHUNKING__CHUNK_SIZE`.

Env-конфигурация выбрана вместо YAML, потому что один и тот же образ можно
запускать с разными настройками без изменения файлов, а Docker и CI/CD передают
env и секреты штатными средствами.

## Подготовка

До первого запуска нужно восстановить SQLite-каталог и построить vector store.
Embeddings и остальные RAG-артефакты не пересчитываются при каждом старте.

### Для локального CLI и API

```bash
just prepare_agent
```

Команда использует зависимости из локального `.venv` и записывает каталог,
RAG-артефакты и кеш модели в `runtime/` внутри проекта. Одной подготовки
достаточно и для CLI, и для локального HTTP API.

### Для Docker

```bash
just docker_build
just docker_prepare
```

- `docker_build` устанавливает зависимости внутрь образа, поэтому локальный
  `.venv` контейнеру не нужен;
- `docker_prepare` запускает восстановление каталога и все стадии RAG внутри
  одноразовых контейнеров, записывая результат в Docker volume с именем из
  `DOCKER_RUNTIME_VOLUME_NAME`.

Локальная команда `just prepare_agent` пишет в `runtime/` проекта и не
подготавливает Docker volume.

SQLite-база памяти и её таблица создаются автоматически при инициализации
агента — как при локальном запуске, так и в Docker.

### Чистая подготовка

Для полного локального сброса и повторной подготовки:

```bash
just clear_runtime
just prepare_agent
```

Для полного сброса данных в Docker volume и повторной подготовки:

```bash
just docker_clear_runtime
just docker_prepare
```

Подготовку достаточно повторять после очистки runtime, изменения CSV-каталога,
документов базы знаний или настроек RAG.

## Запуск

### CLI

```bash
just run_agent_cli
```

CLI принимает реплики до команды `exit` или `выход`. Дополнительные аргументы
передаются после имени recipe:

```bash
just -- run_agent_cli --user-id customer-1 --session-id consultation-1 --log-level info --trace
```

| Аргумент | Назначение |
| --- | --- |
| `--user-id ID`, `--user_id ID` | Владелец долговременной памяти; по умолчанию `local_user`. |
| `--session-id ID`, `--session_id ID` | Текущая сессия; без аргумента создаётся UUID. |
| `--trace` | Печатать в `stderr` структурированный результат запроса. |
| `--log-level LEVEL` | Уровень логирования: `critical`, `error`, `warning`, `info` или `debug`; по умолчанию `info`. |
| `-h`, `--help` | Показать справку CLI. |

Проверочные реплики приведены в разделе [Проверка CLI](#проверка-cli).

### Локальный HTTP API

```bash
just run_agent_api
```

Приложение создаёт один экземпляр агента, поэтому short-term history одной
`session_id` сохраняется между HTTP-запросами, пока работает процесс. Адрес,
порт и уровень логов задаются `API_HOST`, `API_PORT` и `API_LOG_LEVEL`.

Порядок проверки API и отправки реплик описан в разделе
[Проверка через Swagger](#проверка-через-swagger).

### Docker

Приложение FastAPI, агент и embedded Qdrant работают в одном
контейнере. После сборки образа и подготовки volume запустите API:

```bash
just docker_run_agent_api
```

Каталог, память, RAG-артефакты и кеш embedding-модели сохраняются в persistent
volume. После запуска используйте инструкцию
[Проверка через Swagger](#проверка-через-swagger).

## Проверка

### Тестовые диалоги

Используйте следующие реплики в CLI или Swagger. Trace и логи позволяют
проверить, какие компоненты действительно участвовали в ответе.

1. LLM + RAG:

   ```text
   Какой WAN-порт нужен для тарифа 1 Гбит/с?
   ```

   Ожидается вызов `search_knowledge_base` и ответ с citation.

2. Только LLM, без поисковых Tools:

   ```text
   Чем ты можешь помочь при выборе сетевого оборудования?
   ```

3. Memory + LLM — отправьте две отдельные реплики с одним `user_id`.

   Сообщение 1:

   > Запомни мой бюджет 10000 рублей

   Сообщение 2:

   > Какой бюджет я указал?

4. Memory + RAG + LLM — отправьте две отдельные реплики с одним `user_id`.

   Сообщение 1:

   > Запомни, что скорость моего тарифа 1000 Мбит/с

   Сообщение 2:

   > Какой WAN-порт нужен для моего тарифа?

5. Каталог + LLM:

   ```text
   Покажи USB-адаптер Wi-Fi 6 до 7000 рублей
   ```

`user_id` определяет владельца долговременных предпочтений. Один идентификатор
нужно использовать повторно, чтобы агент учитывал сохранённые факты после новой
сессии. `session_id` связывает short-term history текущего диалога; эта история
живёт до завершения процесса или явного окончания CLI-сессии. Одну `session_id`
нельзя использовать для разных пользователей.

### Проверка CLI

Запустите CLI с подробными логами и trace:

```bash
just -- run_agent_cli --user-id customer-1 --session-id check-1 --log-level debug --trace
```

По очереди вводите реплики из [Тестовых диалогов](#тестовые-диалоги). Для
сценариев памяти не меняйте `user_id`; для проверки short-term history также
оставьте прежнюю `session_id` в рамках запущенного процесса.

`--trace` печатает JSON со статусом, источниками, citations, артикулами,
`tool_calls`, `memory_used`, ошибками и идентификаторами. Логи показывают
загрузку памяти, план, вызовы Tools, сборку контекста и обращения к LLM.
`component` в событии ошибки указывает место сбоя, `error_code` — стабильный код,
а `error_type` и `reason` — техническую причину.

### Проверка через Swagger

Сначала убедитесь, что процесс и runtime готовы:

```bash
just api_health
just api_ready
just open_swagger
```

- `GET /health` проверяет HTTP-процесс.
- `GET /ready` возвращает `200`, когда агент, каталог и vector store готовы;
  иначе возвращает `503`.
- `POST /chat` выполняет одну реплику диалога.

При недоступности LLM или другой обязательной зависимости `POST /chat`
возвращает `503`, а при некорректном ответе LLM — `502`. Тело ответа при этом
сохраняет структурированные поля `status` и `errors`.

В Swagger UI откройте endpoint, нажмите **Try it out**, заполните тело запроса и
нажмите **Execute**. Пример для `POST /chat`:

```json
{
  "user_id": "customer-1",
  "session_id": "swagger-check-1",
  "message": "Какой WAN-порт нужен для тарифа 1 Гбит/с?"
}
```

Для сценариев памяти повторяйте запрос с теми же `user_id` и `session_id`, меняя
только `message`. Ответ содержит статус, текст, citations, артикулы, Tool calls,
использованную память и контролируемые ошибки; внутренние prompts, embeddings и
секреты API не возвращает.

При `API_LOG_LEVEL=debug` после каждого `POST /chat` в лог API записывается
событие `agent_trace` с тем же структурированным результатом. При уровне `info`
остаются только основные события выполнения без полного trace.

### Автоматические проверки

```bash
just lint
just test
```

`just test` восстанавливает каталог, пересобирает vector store, выполняет тесты
с coverage и очищает runtime. Coverage выводится в терминал и сохраняется в
`tests/coverage_report.json`; измеряется пакет `ai_agent`. Контрольный результат:
**66 passed**, покрытие — **84%**.

Сценарные тесты не обращаются к облачной LLM. В `LLMService` передаётся
детерминированный `ScriptedChatClient`, который возвращает подготовленные
типизированные ответы планировщика, фильтров и финального ответа. Сборка
prompts, Pydantic-валидация, оркестратор, память, SQLite-каталог, ToolRegistry и
обработчики остаются настоящими. Отдельные клиенты воспроизводят недоступность и
некорректный ответ LLM.

Пять обязательных кейсов задания:

- `TC-RAG-001` — RAG возвращает подтверждённый контекст и citation;
- `TC-CATALOG-001` — каталог вызывается без RAG и фильтрует товары;
- `TC-MEMORY-007` — сохранённый бюджет влияет на следующий подбор;
- `TC-RAG-NOT-FOUND-001` — отсутствие знаний даёт `not_found` без выдумок;
- `TC-RAG-ERROR-001` — отказ retrieval обрабатывается без падения и повторного
  Tool-цикла.

Ещё 32 кейса покрывают комбинированные сценарии, отдельные Tools, уточнение,
непрофильные вопросы, отсутствие товаров, недоступность зависимостей, защиту от
выдуманного артикула, операции памяти, изоляцию `user_id` и `session_id`,
комбинированный статус и контролируемые ошибки. Некорректные числовые значения
в `TC-MEMORY-008` и `TC-MEMORY-009` дают `needs_input` и не попадают в SQLite.

Результаты сохраняются в `tests/tests_report.json`. Этот файл содержит
определения сценариев, ожидаемое поведение и фактические результаты текущего
запуска: ответ, источники, артикулы, ошибки, память и полные Tool calls. Перед
pytest прежние фактические данные очищаются; отсутствие нового результата
делает запуск неуспешным. Обязательные ID перечислены в `required_test_ids`, а
их записи помечены `"required": true`.

Memory не является Tool: она загружается перед планированием каждого запроса и
передаётся LLM как контекст. Поэтому её фактическое использование записывается
в `actual.memory`, а операции, выбранные планировщиком, — в `tool_calls`.

Итоговый статус комбинированного поиска определяется по источнику, обязательному
для цели запроса: пустой дополнительный RAG не отменяет найденный товар, а
пустой обязательный каталог приводит к `not_found`. Планировщик вызывается один
раз и выбирает не более `AGENT_MAX_ACTIONS_PER_REQUEST` уникальных действий;
поддерживаемое значение по умолчанию — `2`.

## Ограничения

- Поддерживается только домашнее сетевое оборудование из локального каталога.
- Цены и остатки не обновляются из внешней системы магазина.
- Для рабочего запуска требуется доступ к настроенной облачной LLM.
- Память не сохраняет адреса, платёжные данные, пароли и токены.
