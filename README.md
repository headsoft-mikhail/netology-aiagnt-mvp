# MVP консультанта по сетевому оборудованию

Агент интернет-магазина подбирает домашнее сетевое оборудование и отвечает на
вопросы о выборе, совместимости и настройке. Рекомендации строятся по локальной
базе знаний, а цены, характеристики и наличие берутся из SQLite-каталога.

## Возможности

- `search_knowledge_base` ищет инструкции и критерии выбора через RAG.
- `search_products` фильтрует актуальный каталог по категории, характеристикам,
  цене, брендам и наличию.
- CSV-слепок содержит 35 устройств пяти категорий; `product_code` — артикул
  товарной позиции, а не серийный номер отдельного экземпляра.
- Long-term memory хранит только явно сохранённые предпочтения пользователя.
- Short-term memory поддерживает контекст текущего диалога.

## Сценарий и архитектура

Основной путь:

```text
пользователь → AgentRunner → Memory → LLM-планировщик
             → обработчики → ToolRegistry
             → search_knowledge_base → RAG-контекст
             → LLM-фильтры → search_products → товары
             → LLM → итоговый ответ
```

Вызовы Tools, их параметры и результаты сохраняются в trace. Итоговый ответ
может содержать только товары, которые вернул каталог. RAG-ответ возвращает
структурированные citations с документом, chunk, разделом и score.

Основные компоненты:

- `src/ai_agent/agent.py` — оркестратор и последовательность шагов;
- `src/ai_agent/factory.py` — единая сборка агента для CLI и HTTP API;
- `src/ai_agent/handlers/` — обработчики памяти, планирования, RAG, каталога и
  финального ответа;
- `src/ai_agent/cli.py` — интерактивный CLI;
- `src/ai_agent/service/` — HTTP API на FastAPI и app-scoped зависимости
  `modern-di`;
- `src/ai_agent/llm/` — Pydantic AI-клиент для OpenAI-compatible API и
  типизированные ответы планировщика, фильтров каталога и финального ответа;
- `src/ai_agent/tools/` — общий протокол, реестр и Tools поиска знаний и товаров;
- `src/ai_agent/rag/` — подготовка источников и retrieval;
- `src/ai_agent/catalog/` — CSV-слепок и SQLite-каталог;
- `src/ai_agent/memory/` — долговременная и сессионная память;
- `tests/` — unit-, сценарные и smoke-тесты.

## Установка

Локальная инструкция рассчитана на macOS. Требуются Homebrew и `just`; команды
установки окружения для других платформ не проверялись.

```bash
just setup
just python 3.14.5
just lock && just install
```

Создайте `.env` из `.env.example` и укажите ключ LLM:

```bash
cp .env.example .env
```

В `.env.example` уже заданы все несекретные настройки. Пустым оставлен только
`LLM_API_KEY`; укажите в локальном `.env` реальный токен. Конфигурация читается
через `pydantic_settings` с префиксами `LLM_`, `CATALOG_`, `MEMORY_`, `API_`,
`AGENT_`, `RAG_RETRIEVAL_` и `RAG_PIPELINE_`. Вложенные параметры RAG pipeline
разделяются двумя подчёркиваниями, например
`RAG_PIPELINE_CHUNKING__CHUNK_SIZE`.

Несекретные параметры имеют рабочие defaults в конфигурационных моделях;
значения из окружения переопределяют их. Поэтому обязательным внешним значением
для реального обращения к модели остаётся только `LLM_API_KEY`.

Команды `just` загружают `.env` через `uv run --env-file .env`. Объекты
`BaseSettings` читают уже сформированное окружение и сами файл `.env` не
открывают.

Настоящий `.env` не добавляется в Git. YAML-конфиги приложению не требуются.

## Подготовка и запуск

Каталог и vector store подготавливаются до запуска агента:

```bash
just prepare_agent
```

Подготовка не выполняется при каждом старте агента: embeddings и vector store
пересобираются только явной командой. Запуск проверяет наличие каталога и vector
store и завершается с понятной ошибкой, если они не подготовлены.

Vector store — сгенерированный runtime-артефакт, а не часть исходного кода.
`just prepare_agent` строит его из версионируемых документов до запуска CLI или
API. FastAPI не запускает тяжёлый pipeline в startup: app-scoped зависимость
`AgentRuntime` использует готовый артефакт, а `/ready` проверяет наличие нужной
Qdrant-коллекции.

Интерактивный режим:

```bash
just run_agent
```

HTTP API:

```bash
just run_agent_api
```

Приложение создаёт один экземпляр агента при старте, поэтому short-term history
одной `session_id` сохраняется между запросами, пока работает процесс API.

Проверка процесса и готовности runtime-данных:

```bash
set -a
source .env
set +a
curl "http://127.0.0.1:${API_PORT}/health"
curl "http://127.0.0.1:${API_PORT}/ready"
```

Запрос к агенту:

```bash
curl -X POST "http://127.0.0.1:${API_PORT}/chat" \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"customer-1","session_id":"consultation-1","message":"Как выбрать роутер для тарифа 1 Гбит/с?"}'
```

`GET /health` проверяет только HTTP-процесс. `GET /ready` возвращает `200`,
когда агент, каталог и vector store готовы, иначе `503`. `POST /chat`
возвращает статус и ответ агента, citations, артикулы, Tool calls, использованную
память и контролируемые ошибки. Внутренние prompts, embeddings и секреты через
API не возвращаются. Адрес, порт и уровень логов задаются переменными
`API_HOST`, `API_PORT` и `API_LOG_LEVEL`.

## Запуск в Docker

Docker Compose не требуется: API и embedded Qdrant работают в одном
контейнере. Имя образа и named volume задают `DOCKER_IMAGE_NAME` и
`DOCKER_RUNTIME_VOLUME_NAME` из `.env`. В volume хранятся каталог,
долговременная память, vector store, промежуточные данные RAG и кеш
embedding-модели.

Сначала соберите образ и один раз подготовьте runtime-данные:

```bash
just docker_build
just docker_prepare
```

`docker_prepare` восстанавливает SQLite-каталог из CSV и с нуля строит vector
store. При последующих запусках эту команду нужно повторять только после
изменения CSV-каталога, документов базы знаний или настроек RAG pipeline.

Запустите HTTP API:

```bash
just docker_run_agent_api
```

Команда передаёт все настройки из локального `.env`, публикует порт `API_PORT`
и подключает тот же persistent volume к `/app/runtime`. Пути к каталогу,
памяти, RAG-артефактам и кешу embedding-модели в `.env` относительны каталога
проекта, поэтому одинаково работают локально и внутри образа. Каталог
`runtime/` содержит только генерируемые данные и не добавляется в Git. Обычный
запуск не вычисляет embeddings заново. Загрузите значения `.env` в текущую
оболочку и проверьте сервис:

```bash
set -a
source .env
set +a
curl "http://127.0.0.1:${API_PORT}/health"
curl "http://127.0.0.1:${API_PORT}/ready"
```

В образе настроен Docker healthcheck по `/ready`. Если volume ещё не
подготовлен, процесс API запустится, но контейнер получит состояние `unhealthy`,
а `/ready` вернёт `503`.

Идентификаторы, логи и структурированный trace можно включить аргументами:

```bash
just -- run_agent --user-id customer-1 --verbose --trace
```

`--debug` добавляет Python traceback для технической диагностики. `--trace` и
`--debug` можно использовать вместе: первый показывает структурированный путь
агента, второй — цепочку исключений. Логи выводятся в `stderr`, отдельно от
ответа агента.

В событии `request_failed` поле `component` показывает место сбоя (`llm`,
`memory`, `search_products` или `search_knowledge_base`), `error_code` —
стабильный код для приложения, а `error_type` и `reason` уточняют техническую
причину, если при сбое было перехвачено исключение.

### Аргументы CLI агента

Аргументы передаются после `just -- run_agent`.

| Аргумент | Назначение |
| --- | --- |
| `--user-id ID`, `--user_id ID` | Владелец долговременной памяти. По умолчанию `local_user`. |
| `--session-id ID`, `--session_id ID` | Идентификатор текущего диалога. По умолчанию генерируется UUID. |
| `--trace` | Печатает в `stderr` JSON-ответ целиком: статус, источники, артикулы, Tool calls, использованную память, ошибки и идентификаторы запроса/сессии. |
| `--verbose` | Печатает в `stderr` основные этапы: память, выбор действий, вызовы Tools, сборку контекста и обращения к LLM. |
| `--debug` | Включает наиболее подробные диагностические логи и stack trace при ошибке; одновременно с `--verbose` не используется. |
| `-h`, `--help` | Показывает встроенную справку CLI. |

### `user_id` и `session_id`

- `user_id` определяет владельца долговременных предпочтений. Используйте один
  и тот же идентификатор, чтобы агент учитывал сохранённый бюджет, бренды и
  другие разрешённые факты в следующих запусках.
- `session_id` связывает сообщения одного текущего диалога. В интерактивном
  режиме история живёт до выхода из процесса; после `end_session` она очищается.
- Не используйте одну `session_id` для разных `user_id`: агент отклоняет такой
  запрос.

Проверка памяти и продолжения одной сессии:

```bash
just -- run_agent --user-id customer-1 --session-id consultation-1 --verbose
```

В открывшемся диалоге сначала попросите: `Запомни мой бюджет 10000 рублей`,
затем: `Подбери роутер для тарифа 1 Гбит/с`. После перезапуска с тем же
`user_id` долговременный бюджет останется доступен; история реплик — нет.

## Проверка

```bash
just lint
just test
```

`just test` восстанавливает каталог, пересобирает vector store, выполняет все
тесты и затем очищает runtime-данные.

Сценарные тесты не обращаются к облачной LLM. Вместо сетевого клиента в
`LLMService` передаётся детерминированный `ScriptedChatClient`, который по
очереди возвращает подготовленные JSON-ответы планировщика, построителя фильтров
и финального ответа. Сборка промптов, Pydantic-валидация ответов, оркестратор,
память, SQLite-каталог, ToolRegistry и обработчики при этом остаются настоящими.
Отдельные тестовые клиенты воспроизводят недоступность и некорректный ответ LLM.
Реальная облачная LLM используется при запуске агента через CLI с `.env`.

Обязательные кейсы задания:

- `TC-RAG-001` — RAG находит подтверждённый контекст, а ответ содержит source и
  структурированную citation;
- `TC-CATALOG-001` — каталог вызывается без RAG и возвращает товар по фильтрам;
- `TC-MEMORY-007` — первый запрос сохраняет бюджет, а второй использует его в
  фильтре каталога и итоговом ответе;
- `TC-RAG-NOT-FOUND-001` — при отсутствии релевантных знаний агент возвращает
  `not_found`, пустые citations и не просит LLM придумать ответ;
- `TC-RAG-ERROR-001` — отказ retrieval даёт контролируемую ошибку без повторного
  Tool-цикла и аварийного завершения.

Ещё 32 кейса проверяют основные комбинированные сценарии, отдельные вызовы каждого
Tool, уточнение, непрофильные вопросы, отсутствие товаров разных категорий,
валидацию и недоступность зависимостей, защиту от выдуманного артикула, операции
памяти, изоляцию `user_id`, контекст/изоляцию `session_id`, комбинированный
статус RAG + каталог и контролируемые ошибки. Для каждого кейса записаны `id`,
`type`, запрос, ожидаемый и фактический результат, citations, вызванные Tools и
признак прохождения. В начале отчёта поле `required_test_ids` отдельно содержит
ID пяти обязательных проверок; сами записи помечены `"required": true`.

Результаты сохраняются в `tests/tests_report.json`. Этот файл одновременно
содержит определения отчётных сценариев: их ID, запросы и ожидаемое поведение.
Сценарные тесты получают запросы оттуда и связываются с кейсами маркером
`report_case`. Перед запуском pytest очищает прежние фактические результаты, а
тесты записывают текущие статус, ответ, источники, артикулы, ошибки, работу
памяти и полные вызовы Tools с входами и выходами. После набора обновляется
`passed`; кейс без нового фактического результата делает запуск неуспешным.
Поэтому старые `actual` и `tool_calls` не могут выдать себя за свежий отчёт.

Memory не является Tool: она загружается перед планированием каждого запроса и
передаётся модели как часть контекста. Поэтому в отчёте работа памяти находится
в отдельном объекте `actual.memory`, а выбираемые планировщиком операции поиска
— в `tool_calls`. Кейс `TC-MEMORY-007` выполняет два запроса через агента:
сохраняет бюджет, затем проверяет его фактическое влияние на фильтр каталога и
итоговый ответ. Некорректные числовые значения в кейсах `TC-MEMORY-008` и
`TC-MEMORY-009` дают `needs_input` и не записываются в SQLite.

Для комбинированного поиска итоговый статус определяется по обязательному для
цели источнику: при подборе товара пустой дополнительный RAG не отменяет
успешный результат каталога, а пустой каталог приводит к `not_found`.

Планировщик вызывается один раз на пользовательский запрос. Схема ответа LLM
разрешает от одного до `AGENT_MAX_ACTIONS_PER_REQUEST` уникальных действий;
значение по умолчанию и максимальное поддерживаемое значение — `2`. Поэтому в
одном запросе агент может последовательно вызвать не более двух поисковых
Tools, без повторов и бесконечного агентского цикла.

Coverage выводится в терминал и сохраняется в
`tests/coverage_report.json`. Отчёт измеряет только пакет `ai_agent`.

Контрольный запуск `just test`: **65 passed**, покрытие — **84%**.

### GitHub Actions

Workflow `.github/workflows/ci.yml` запускает job `quality` для pull request в
`main` и повторно после успешного merge. Job выполняет форматтеры, линтеры и
проверку типов, затем убеждается, что они не изменили файлы.

## Служебные команды

| Команда | Назначение |
| --- | --- |
| `just prepare_agent` | Восстановить каталог и полностью пересобрать vector store перед запуском. |
| `just run_agent_api` | Запустить FastAPI на адресе и порту из `API_HOST` и `API_PORT`. |
| `just docker_build` | Собрать локальный Docker-образ приложения. |
| `just docker_prepare` | Восстановить каталог и построить RAG-данные в persistent volume. |
| `just docker_run_agent_api` | Запустить HTTP API из образа с подготовленным persistent volume. |
| `just catalog_restore` | Заново создать SQLite-каталог из версионируемого CSV-слепка. |
| `just catalog_clear` | Удалить сгенерированную БД каталога. |
| `just memory_clear` | Удалить всю локальную долговременную память. |
| `just rag_rebuild` | Очистить и выполнить все стадии подготовки RAG. |
| `just rag_prepare` | Подготовить исходные документы. |
| `just rag_chunk` | Разбить подготовленные документы на фрагменты. |
| `just rag_embedding` | Рассчитать embeddings фрагментов. |
| `just rag_vectorstore` | Создать vector store из готовых embeddings. |
| `just rag_clear` | Удалить все сгенерированные данные RAG. |
| `just clear_runtime` | Очистить память, каталог и сгенерированные данные RAG. |

У служебных Python CLI нет дополнительных флагов, кроме автоматического
`-h`/`--help`; выбор операции сделан отдельными командами `just`.

## Ограничения

- Поддерживается только домашнее сетевое оборудование из локального каталога.
- Цены и остатки не обновляются из внешней системы магазина.
- Для рабочего запуска требуется доступ к настроенной облачной LLM.
- Память не сохраняет адреса, платёжные данные, пароли и токены.

Сбросить память, каталог и vector store можно командой `just clear_runtime`.
После неё для запуска агента снова требуется `just prepare_agent`.
