# Возможный рефакторинг

Текущее решение пригодно для учебного MVP. Следующие изменения сделали бы
структуру однороднее и упростили бы развитие проекта, но не обязательны для
исходного задания.

## Высокий приоритет

1. Разделить `agent.py` на оркестратор и обработчики действий. В оркестраторе
   оставить последовательность шагов, а работу с RAG, каталогом, памятью и
   финальным ответом перенести в отдельные обработчики.
2. Добавить единый composition root, например `bootstrap.py`. Только он должен
   читать конфигурацию и создавать реализации репозиториев, LLM и Tools; CLI
   будет отвечать лишь за аргументы и вывод.
3. Унифицировать пакеты `catalog`, `memory`, `rag` и `llm`: использовать в каждом
   одинаковые роли файлов (`config.py`, `models.py`, `service.py` или
   `repository.py`, при необходимости `cli.py`).
4. Описать общий протокол Tool и реестр Tools. Тогда имя, входной контракт,
   выполнение, trace и обработка ошибки не придётся связывать вручную в агенте.
5. Убрать отдельный `catalog/restore.py`: перенести чтение CSV-слепка и атомарное
   восстановление SQLite в `ProductsRepository.restore_from_snapshot()`. CLI и
   тесты будут работать через один интерфейс репозитория, а вся ответственность
   за устройство каталога останется в одном модуле.

## Средний приоритет

1. Ввести интерфейсы репозиториев памяти и каталога. Сценарные тесты смогут
   подменять хранилища без знания SQLite, а рабочая реализация останется прежней.
2. Вынести имена событий и безопасные поля логов в один модуль. Это уменьшит
   риск расхождения между логированием, тестами и документацией.
3. Сделать сценарии тестового отчёта единым источником данных: один набор
   фикстур должен запускать проверки и формировать `tests_report.json`, чтобы
   отчёт не расходился с тестами.
4. Развести конфигурацию по назначению: YAML — для несекретных параметров и
   путей, `.env` — только для ключей и параметров внешней LLM.

## Низкий приоритет

1. Перенести тексты пользовательских сообщений из `agent.py` в отдельный
   модуль, если появится локализация или второй интерфейс.
2. Добавить миграции SQLite, когда базы перестанут быть полностью
   восстанавливаемыми из CSV и runtime-данных.
3. Добавить генератор демонстрационных данных каталога, если объём CSV начнёт
   мешать ручному сопровождению.

`SKU` (Stock Keeping Unit) означает складской идентификатор товарной позиции.
В проекте публичное поле теперь называется `product_code`, а в русском
интерфейсе — «артикул»: это не название товара и не серийный номер экземпляра.
